# 保存・移行・画像管理

## 保存先と保証範囲

Tauriの `document_dir()` で取得するOSのドキュメント内の `mizu-pairrank` に、`pairrank.sqlite3` と `images` を保存する。保存先の選択UIは設けず、存在しなければ作成し、既存の保存先は再利用する。旧アプリデータ領域は自動移行・削除しない。ドキュメントの取得や保存先の作成に失敗した場合は起動エラーとし、別の場所へ切り替えない。

[storage.rs](../src-tauri/src/storage.rs) の `PreparedAppData` を起動時に開き、DBと画像サービスで同じディレクトリハンドルを共有する。子の作成・権限修復・同期・削除はハンドルを基点とし、パスの再検証で差し替えを検出する。初期化中に保存先や親の別名の差し替えを検出した場合は両サービスを停止する。画像だけの通常の初期化失敗ではDBを利用できる状態を保つ。

保証範囲は、同一ホストのローカルファイルシステムでOSのロック・同期機能を使う操作。ネットワークファイルシステムや、外部同期による複数端末間の競合は保証しない。

## SQLiteとマイグレーション

[database.rs](../src-tauri/src/database.rs) は回答・評価・順位判定窓を同時に保存する。スキーマは `PRAGMA user_version` の連番で管理し、アプリのリリース番号・[評価モデル](rating.md)のバージョンから独立させる。

新しい空DBは0から初期化し、同版なら更新しない。起動時は保存バージョンを読み、`BEGIN IMMEDIATE` の取得後に再確認する。未適用のSQLすべてとバージョン更新を同じトランザクションで実行し、外部キー整合性を検証してからコミットする。失敗時はスキーマ・データ・バージョンを全体としてロールバックする。未来版のDBと非空の未管理DBは変更せず停止し、自動ダウングレードや初期化による復旧は行わない。

通常操作でもトランザクション内で `user_version` を確認する。書き込みは `BEGIN IMMEDIATE` 後に確認し、終了までロックを保持する。読み取りは版確認とデータ取得を同じスナップショットで行い、途中で他の接続が未来版へ移行した場合は次の操作で拒否する。画像参照の読み取りも対象で、確認に失敗した場合は画像削除を中止する。拒否時は保存版・対応版とアプリ更新の案内を返す。

スキーマ変更時は次の手順に従う。

1. 公開済みの [migrations](../src-tauri/migrations) のSQLを変更せず、次の番号のSQLを追加し、`database.rs` の `MIGRATIONS` に登録する。既存データの変換もSQLに含める。
2. SQLはトランザクション内で実行可能な処理に限定し、`BEGIN` / `COMMIT`、`VACUUM`、外部ファイル操作を含めない。
3. 旧版データから最新への移行と内容保持をテストする。ランナーの複数段階更新・再実行防止・後段失敗時の全体ロールバック・未来版と未管理DBの拒否も維持する。

## ディレクトリ固定とSQLite更新時の確認

[sqlite_vfs.rs](../src-tauri/src/sqlite_vfs.rs) のVFSとOSフックは、DB本体・journal・WAL・SHMを同じ保存先から解決する。基底VFSはmacOSが `unix-posix`、Linuxが `unix`、Windowsが `win32`。ロック・共有メモリ・回復は同梱SQLiteを使い、接続終了後もSQLiteが保持するファイル記述子・SHMハンドルが閉じられるまで保存先を保持する。Unixはディレクトリ相対のOS操作、Windowsの作成・列挙・削除は直接ハンドルを受け取るOS操作を使う。Windowsのcap-stdでハンドルからパスを復元するAPIは、この保証の根拠にしない。

起動時に `SQLITE_SOURCE` と `sqlite3_sourceid()`、必要なコンパイル設定、基底VFSと必須フックを照合し、不一致ならDBを開かない。SQLite・`rusqlite` / `libsqlite3-sys` の更新時はamalgamationのDB・副ファイル・親ディレクトリへのOS呼び出しとフックの名前・ABIを確認し、対応実装と期待source IDを一緒に更新する。期待source IDだけを更新しない。

更新後は、差し替え先の内容・権限の保持、journal / WAL回復、複数接続・別プロセスのロックと接続終了を含む全テストをLinux・macOS ARM64・Windows x64 / ARM64で実行する。通常の回復とロックを維持し、hot journalを一律に拒否・削除しない。

## 管理画像

新規画像の `ImageAsset.path` はASCIIのUUIDファイル名とし、Rust側で保存先の `PathBuf` と結合する。専用の `pairrank-image` protocolで管理画像を配信し、Unixの保存先が非UTF-8でも表示・削除できる。既存DBの絶対UTF-8パスは書き換えず、従来のasset protocolによる表示と管理ディレクトリ内に限定した削除を維持する。

[lib.rs](../src-tauri/src/lib.rs) は画像配信を専用セマフォで同時4件に制限し、DB・検索・取り込みの実行枠から独立させる。超過要求はワーカーや画像バッファを確保する前に非同期で待機する。枠は画像の読み取りから `responder.respond` の終了までワーカーが保持し、キャンセル後も続くワーカーを数え、正常終了・エラー・panicの巻き戻しで解放する。待機要求数に固定上限はなく、配信数は内部定数で公開設定にしない。

[images.rs](../src-tauri/src/images.rs) は起動時に保存先の排他ロックを取得できた場合だけ、DB参照のない管理UUID画像を回収する。全参照の照合が完了するまで削除せず、旧絶対パスは親ディレクトリの同一性を調べて別名経由の参照も保持する。管理外ファイル・シンボリックリンクは保持し、DB参照を読めなければ削除しない。

画像サービスは生存中に共有ロックを保持し、別インスタンスが動作中なら回収を延期する。Unixは画像ディレクトリ自体、Windowsは削除・名前変更の共有を許可しない `.images.lock` のハンドルをロックする。保存からDB登録までの画像と、キャンセル後も続く保存タスクを保護し、プロセス終了時にOSがロックを解放する。旧Unixロックファイルは使わず残す。

## バックアップと復元

同じ端末・同じ保存先への停止中のバックアップ・復元に対応する。全アプリ・DB接続・保存先を変更する外部同期を止め、DB・残存副ファイル・画像を含むフォルダー一式をコピーする。復元は現在のフォルダーを退避してから元の場所へ戻し、古い副ファイルと混在させない。利用者向けの手順と資格情報の扱いは[README](../README.md#バックアップと復元)を参照する。

稼働中の直接同期やDB・副ファイルの個別置換は非対応。保持済みディレクトリだけでは、別DBのjournalによる誤復旧や、副ファイル名へ置換された無関係なファイルの削除を防げない。アプリ内バックアップや端末間同期の機能は持たない。
