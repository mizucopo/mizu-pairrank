# DBと画像の保存先を起動時のディレクトリに固定する

利用者が保存データを確認できるよう、保存先はTauriの `document_dir()` で取得するOSのドキュメント内の `mizu-pairrank` に固定する。`pairrank.sqlite3` と `images` を同じ保存先に置き、保存先の選択UIは設けない。保存先がなければ作成して空の状態から開始し、既存の保存先は再利用するが、旧アプリデータ領域の移行・自動削除は行わない。ドキュメントの取得や保存先の作成に失敗した場合は起動エラーとして扱い、別の保存先にはフォールバックしない。

保存先のパスを検証してから子ファイルを開くまでにディレクトリや親の別名が差し替わると、別のDBを更新したり、元のDB参照で置換先の画像を削除したりする。起動時に保存先を `PreparedAppData` として開き、DBと画像サービスで同じディレクトリハンドルを共有する。子の作成・権限修復・同期・削除はそのハンドルを基点とし、パスの再検証は差し替えの検出に使う。差し替えを検出した起動では両サービスを停止し、画像だけの通常の初期化失敗ではDBを利用できる状態を保つ。

SQLiteには内部名を使うVFSとOS呼び出しのフックを追加し、DB本体・journal・WAL・SHMを同じ保存先から解決する。ロック、共有メモリ、回復処理は同梱SQLiteの実装を使い、macOSは `unix-posix`、Linuxは `unix`、Windowsは `win32` を基底VFSとする。SQLiteが接続終了後も保持するファイル記述子やSHMハンドルが閉じられるまで、保存先の寿命を維持する。Unixのpathname操作はディレクトリ相対のOS操作へ接続し、Windowsのディレクトリ作成・列挙・削除には直接ハンドルを受け取るOS操作を使う。Windowsのcap-stdにはハンドルからパスを復元して操作するAPIがあるため、該当する操作を安全性の根拠にしない。

フックは同梱SQLiteのOS実装に依存するため、起動時に [sqlite_vfs.rs](../../src-tauri/src/sqlite_vfs.rs) の `SQLITE_SOURCE` と `sqlite3_sourceid()`、必要なコンパイル設定、基底VFSと必須フックの存在を照合し、不一致ならDBを開かない。SQLiteや `rusqlite` / `libsqlite3-sys` の更新時は、更新後のamalgamationでDB・sidecar・親ディレクトリに対するOS呼び出しとフックの名前・ABIを再確認し、対応する実装と期待source IDを一緒に更新する。そのうえで、差し替え先の内容・権限の保持、journal / WALの回復、複数接続・別プロセスのロックと接続終了を含む全テストを、Linux・macOS ARM64・Windows x64 / ARM64のネイティブ環境で通す。期待source IDだけを更新して互換性確認を省略しない。

保証範囲は同一ホストのローカルファイルシステムと、そのOSのロック・同期機能を使う操作とする。ネットワークファイルシステムの動作や外部同期による複数端末間の競合は保証に含めない。公開コマンド、フロントエンドの型、DBスキーマ、画像のUUID参照と既存の絶対パス参照は変更しない。

## 停止中のバックアップと復元

[Issue #25](https://github.com/mizucopo/mizu-pairrank/issues/25)では、同じ端末・同じ保存先への停止中のバックアップと復元に対応する。全アプリ・DB接続・保存先を変更する外部同期を停止し、DB・残存する副ファイル・画像を含む保存先フォルダーを一式でコピーする。復元時は現在のフォルダーを退避し、古い副ファイルと混在させず元の場所へ戻す。利用者向けの手順は[README](../../README.md#バックアップと復元)に記載する。現状はこの手順で要件を満たせるため、アプリ内バックアップ機能や端末間同期は追加しない。

稼働中の直接同期と、DB・副ファイルの個別置換は非対応とする。別DBのjournalによる誤った復旧や、副ファイル名へ置換された無関係なファイルの削除によるデータ消失は、保持済みディレクトリだけでは防げない。これらの操作を技術的に防止したとは扱わず、対応範囲と手順の明確化を本Issueの完了とする。

通常のjournal / WAL回復とSQLiteのロックに従う複数接続は引き続き維持し、hot journalを一律に拒否・削除しない。[ADR 0002](0002-sqlite-migrations.md)のマイグレーションの原子性・データ保持も維持する。本件では実装を変更せず、将来保存処理を変更する場合は既存の回復・ロック・マイグレーションの回帰テストを通す。
